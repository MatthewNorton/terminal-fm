# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Terminal FM** — a portable, continuous music player for the Claude CLI. A detached background daemon shuffles MP3 and WAV tracks from a local library forever; new tracks are generated on demand (Stability AI text-to-audio). Between tracks a **DJ voice** reads lines Claude queues and recaps of what Claude just finished, spoken verbatim by a TTS chain (Kokoro-82M preferred, the system voice otherwise). No language model is involved in the DJ.

The user drives this through the radio skill (`skills/tfm/SKILL.md` in this repo, `/tfm` on both installs, `/terminal-fm:tfm` in full), which maps natural language to `radio.py` subcommands. The Claude Code statusline shows the now-playing track.

**Plugin packaging.** The repo is the `terminal-fm` Claude Code plugin and its own marketplace (`digitalbyte`, `"source": "./"`): `.claude-plugin/plugin.json` + `marketplace.json`, `skills/tfm/SKILL.md`, `hooks/hooks.json` + `hooks/radio-hook.sh`, `statusline.py`. Component paths are discovered by convention, so the manifest lists none. Three things follow from how Claude Code loads plugins: the skill body spells out `python3 "${CLAUDE_PLUGIN_ROOT}/radio.py"` (`python`, then `py`, on Windows) because that variable is substituted in skill Markdown but not exported to the Bash tool (confirmed with `--plugin-dir`); a plugin can't set `statusLine`, hence `statusline.py` plus the SessionStart copy; and this file lives at `.claude/CLAUDE.md`, not the repo root, because `claude plugin validate . --strict` fails on a root `CLAUDE.md` ("not loaded as project context"), while Claude Code still loads `.claude/CLAUDE.md` as project memory and its `@../AGENTS.md` import resolves.

**Names.** The product is Terminal FM, the plugin `terminal-fm` (the GitHub repo's name), the skill `tfm` (`/tfm`, in full `/terminal-fm:tfm`; a plugin skill's `name` also answers to the bare `/<name>` unless another command has it), the data directory `~/.claude/terminal-fm` and its override `TERMINAL_FM_HOME`. The skill folder is `skills/tfm` because a personal skill also answers to its folder name.

**Plugin features deliberately not used.** The data directory stays `~/.claude/terminal-fm` (or `TERMINAL_FM_HOME`) rather than `${CLAUDE_PLUGIN_DATA}`, which Claude Code deletes on uninstall unless `--keep-data` is passed and would take the library and the key with it; the models go there too, and `kokoro/.gitkeep` / `llm/.gitkeep` mark where on the manual route (an installed plugin never reads its own copies of those folders). The key stays with `radio key` rather than a `sensitive` `userConfig` value, which Claude Code hands to hooks (`CLAUDE_PLUGIN_OPTION_<KEY>`) but not to the Bash tool that runs `gen`. There is no `bin/` launcher: `bin/` is on the Bash tool's PATH only, and claude.ai and Cowork refuse to install a plugin that has one (plugin manifest reference).

**First-run help.** The first real install, a clean Windows user whose only `python` was the Microsoft Store alias, failed at the first command and Claude spent five commands searching the disk. The fixes span files: the SessionStart note above; the skill's rule to stop and give the install line when no Python runs; `plugin.json`/`marketplace.json` descriptions naming the requirements; and `radio setup` (`cmd_setup`), a read-only wizard: `_setup_required()` builds the required steps in order (Python, player via `_install_cmd`, key, hooks, FFmpeg only under `wav+mp3`, first track) as `(title, done, text)`, and `cmd_setup` prints them as a checklist and spells out only the first unfinished one's `text` between `SETUP_RULE` lines. The extras are one table, `_setup_extras()`: `(name, what it adds, installed check, page function)`, which drives both the extras list and `setup statusline | voice | enhancer | tokens` (`_statusline_page` and so on, each given the same installed answer the list shows). `cmd_setup` still compares its argument to an inline tuple of the four names, because that is where `readme_check.py` reads a command's keywords, and `test_cmd_setup_names_every_extra` keeps that tuple equal to the table. One step at a time because the one-screen checklist it replaced, with the key command run into the end of a sentence, was hard to follow. `_steps()` numbers steps and puts a step's command, path or address on a line of its own (at `STEP_INDENT`) between blank lines, so it copies whole. Hooks count as working when `.hook_seen` exists (written by `cmd_hook` at SessionStart); without it on Windows, `_git_bash()` looks for `bash.exe` where Claude Code does (`CLAUDE_CODE_GIT_BASH_PATH`, else beside `git`). `_statusline_state()` reads `settings.json` (`_settings_file()`: `CLAUDE_CONFIG_DIR` or `~/.claude`) and any script file the command names, looking for `statusline.py` or `nowplaying`, so a custom statusline that already shows the radio counts, and one that doesn't is never offered a replacement snippet. `status` adds a `setup :` line when Python is older than `PY_MIN` or the player, the key or any tracks are missing, from the values it has already looked up. Every no-key message (`gen`, `key show`, `key` without a terminal) and setup's key step print `_key_help()`, whose command is `_self_cmd('key')`, a paste-ready command for this `radio.py` and interpreter (`_console_python()` turns `pythonw.exe` into `python.exe`; `_cmdline()` quotes with `shlex` on POSIX, and on Windows uses forward slashes, double quotes and PowerShell's `&` when the program path has a space, the same quoting the statusline snippet uses), because the old install step that had users find the marketplace folder themselves was where installs stalled. The Python step is done only from `PY_MIN` (3.11, the oldest Python still getting security fixes: 3.10's ended on 2026-10-01 per devguide.python.org/versions), and the install commands name `PY_INSTALL` (3.14), the newest Python winget packaged on 2026-10-19. The optional voice needs dj.py's `PY_VOICE_MAX` (3.13) or older (kokoro-onnx's Requires-Python on PyPI, 2026-10-19), so on a newer Python `_voice_page` swaps its pip step for installing a 3.13 beside it, which `_kokoro_python` then finds, and `readme_check.py` holds every "Python X.Y or older" in README and the skill to it, and README's pip command to `KOKORO_PIP_ARGS`. Files that can't import them are pinned instead: `PythonMinimum` (tests/test_setup.py) checks the hook's `min`, both manifests and CI's oldest Python against `PY_MIN`, and `readme_check.py` checks every minimum and winget Python version README and the skill state. The old-Python step only shows while `radio.py` still compiles on that Python, and CI runs nothing older than `PY_MIN`, so it is best-effort. Open policy question: the hook treats a Python below the minimum as no Python, while `/tfm` commands still run on it and only `setup` and `status` flag it; refusing everywhere or warning everywhere would make it one rule.

**Design constraint that shapes everything:** `radio.py` and `dj.py` are **stdlib-only and cross-platform** (Windows / macOS / Linux). No `pip install`, no third-party imports, no `requirements.txt`. Do not add dependencies to these two files. The *only* component allowed third-party packages is `kokoro_tts.py` (needs `kokoro-onnx` + `soundfile`), and it is invoked as a subprocess through a separately-located Python interpreter precisely so the core stays clean.

**Two roots.** `CODE_DIR = Path(__file__).resolve().parent` is where the scripts and the shipped `prompts/enhance.md` live; `ROOT` is the data directory (`~/.claude/terminal-fm`, or `TERMINAL_FM_HOME`) holding state, config, `.key`, the library, `kokoro/`, `llm/` and logs. `dj.py` computes the same two; `kokoro_tts.py` needs only `ROOT`. Hardcoding `~/.claude/terminal-fm` for both once made a clone elsewhere find no `dj.py`, silently dropping every queued line. On the manual install, with the clone at `~/.claude/terminal-fm`, the two roots are the same folder. A `python radio.py` run from a checkout and an installed plugin's hooks share one data directory, the same arrangement as two sessions.

**Tests.** `python -m unittest discover tests` (stdlib `unittest`) and `python smoke_test.py`, which runs the read-mostly subcommands against a throwaway data directory. CI (`.github/workflows/ci.yml`) runs them alongside `readme_check.py`'s drift layer and `release_check.py`. The ruleset on `main` (changes only through a pull request; no force-push, no deletion) requires one check, CI's `CI passed` job, which fails unless every job in its `needs` passed (a new job goes there too): changing the matrix (a new `PY_MIN`, another OS) needs no ruleset change, but renaming that job does. Otherwise, "running" a change means invoking the subcommands.

**Docs — `README.md` is the source of truth.** README is the full per-command reference, install guide, config shape and troubleshooting guide, and it must always match the code. This file covers the cross-file mechanics and the reasons behind non-obvious choices, and must never contradict README. `skills/tfm/SKILL.md` maps user phrasing to subcommands. Every change to `radio.py`, `dj.py`, `kokoro_tts.py` or `readme_check.py` updates README in the same change and ends with a clean `python readme_check.py` plus `--confirm`. The full rules are in `AGENTS.md` (shared with Codex and other agents), imported here:

## Running / manual testing

- Windows: `python "%USERPROFILE%\.claude\terminal-fm\radio.py" <subcommand> [args]`
- macOS / Linux: `python3 ~/.claude/terminal-fm/radio.py <subcommand> [args]`

The subcommands, aliases and argument grammar are the `COMMANDS` table at the bottom of `radio.py` (no args = `status`) and README's per-command reference. The one- and two-letter short keys (`p` play, `pa` pause, `s` stop, `n`/`sk` skip, and so on) come after the full names in `COMMANDS` on purpose: the unknown-command hint lists the first key for each handler, so it still shows full names.

To debug the "robotic voice" problem, read the tail of `dj_engine.log` — `_log_engine` in `dj.py` writes one tab-separated line per utterance: `<timestamp>  <engine>  <detail>  py=<interpreter basename>  <first 60 chars>`. A `kokoro-fail` line names the exact interpreter and the last non-empty line of its stderr, NULs stripped (onnxruntime's warnings come first, in UTF-16 on Windows), immediately before the `sapi  ROBOTIC FALLBACK - kokoro render failed ...` line. The SAPI detail comes from `_kokoro_why()`, which reads the module global `_kokoro_last` set by `_kokoro_render`: `kokoro not installed` after a `kokoro-skip` (no model, voices or script: the normal zero-model install), `kokoro render failed (see prior kokoro-fail line)` after a `kokoro-fail`, and `kokoro rendered but playback failed` when the WAV rendered but no player could play it. The engine column values never change.

## Architecture — the parts that span files

**Process model.** `radio.py play` spawns `radio.py __daemon` as a fully detached process (`DETACHED_PROCESS`/`CREATE_NEW_PROCESS_GROUP` on Windows, `start_new_session` on POSIX) and returns. The daemon runs `daemon_loop()`: **one track per outer iteration**, re-reading state each time — if `playlist.json` is set it plays that exact ordered selection (looping), otherwise it shuffles the full library a pass at a time. Per track it speaks one queued DJ line, then `Popen`s the player and `proc.wait()`s. Because state is re-read every track, setting/clearing a playlist mid-playback takes effect on the next track. An empty library does not exit the daemon; it polls every 5s. `skip` works by killing the *player* pid so the daemon's `wait()` returns and advances; `stop` kills the *daemon first* (so it can't respawn a player), then `_kill_players_after_daemon()` **re-reads** `state.json` and kills the player it names now, plus the first-read player if that differs (`kill()` skips it when it is no longer that program). The re-read matters: the daemon kill (a `tasklist` check, then `taskkill`) takes long enough that a track can end inside it, and the daemon then starts and records the next player; killing only the first-read pid left that player running untracked (7 of 16 trials when stopping 0.10-0.15 s before the end of a 6 s track). `pause` does the same and computes its offset from the re-read state. **Remaining window:** if the daemon dies after its player `Popen` but before `play_track`'s `write_state`, no state names the new player and nothing kills it; closing that would need a process-tree kill (`taskkill /T`, or a process-group kill on POSIX), which is not done.

**Statusline coupling.** `write_now()` is the only writer of `nowplaying.txt`, and `statusline.py` (like any custom statusline following README's rule) decides "playing vs idle" purely by whether the text contains a `>`: `Terminal FM > <track>` renders magenta with a note glyph, every `Terminal FM | ...` status renders gray. Changing that separator in `radio.py` silently breaks the playing indicator. `statusline.py` honours `TERMINAL_FM_HOME`. `_install_statusline()` (first thing in `cmd_hook` for `SessionStart`, before any early return, so it runs with music stopped too) copies `statusline.py` from `CODE_DIR` to `ROOT` when the bytes differ, via temp file + `os.replace` (the temp file is removed when the rename is refused, as when two plugins' hooks copy at once), and skips when the two are the same file (`os.path.samefile`), as on the manual install.

**Playlists.** `radio.py list` numbers the library and snapshots that order to `last_list.json`; `radio.py play 1,3,5-8` (or `playlist 1,3,5-8`) maps those numbers against the snapshot and writes the ordered track **names** to `playlist.json`. `looks_like_selection`/`parse_selection` handle the `1,3,5-8` grammar (commas/spaces, asc/desc ranges, repeats kept, out-of-range numbers dropped); `cmd_play` delegates to `cmd_playlist` when its non-flag args look like a selection, after dropping the `--say` value (counting it made `play 3,5 --say "..."` ignore the selection and play the whole library). That is how the skill serves `/tfm <genre>` (`/tfm smooth jazz`): it picks matching tracks from `list` and plays them with `play <numbers> --say`, and offers `egen` (credits) only when none fit. `load_playlist` resolves names against the current `OUTDIR`, so a selection whose tracks aren't in the active folder safely reverts to shuffle. `_start_or_jump` nudges a live daemon (kill the player → it advances and re-reads) or starts one; `cmd_shuffle` deletes `playlist.json`. The daemon restarts the playlist from the top when its contents change (tracked via `last_pl`).

**Pause/resume.** `pause` is `stop` plus a snapshot: there is no OS-level pause of the detached player, so `play_track` continuously persists the live position (`player_started` + `player_offset`) to `state.json`, `cmd_pause` reads that to compute the offset and writes `resume.json`, and the next daemon's `_take_resume()` replays that track from a seek offset (no DJ line first) before resuming normal shuffle. `stop` deletes `resume.json` (fresh shuffle); `pause` keeps it. `resume` is just an alias of `play`.

**State files.** Cross-process coordination is entirely through files under the data directory (constants at the top of `radio.py`). Every JSON/text state write goes through `_atomic_write` (temp file + `os.replace`, direct write as a last resort on Windows when a reader holds the file), because a torn `state.json` read as "stopped" and a torn `config.json` used to be replaced with `{}` by `set_config`; it now refuses to overwrite an unparsable config and says so.

- `state.json` — status + daemon/player pids + live position. Each pid is stored with its program name (`daemon_exe`, `player_exe`); `alive(pid, expect)` and `kill(pid, expect)` check the two still match (`tasklist /FO CSV` exact match on Windows, `/proc/<pid>/comm` or `ps -o comm=` on POSIX), so a recycled pid is never reported alive or killed. `daemon_exe` comes from `_self_exe()`, the OS-reported name on POSIX: a macOS framework Python (Homebrew, python.org, Xcode) runs as `Python`, and recording `python3.14` from `sys.executable` made `stop`/`pause` leave a Homebrew-Python daemon playing on a macOS runner. Likewise `player_exe` goes through `PLAYER_PROCESS` (`cvlc` → `vlc`, the program the wrapper execs). A substring match on `tasklist` output is not enough: 20 of 314 running pids were prefixes of another pid when measured.
- `nowplaying.txt` — the statusline reads this (see coupling above)
- `config.json` — settings overlay; `.key` — Stability API key
- `queue/` — one file per pending DJ line (FIFO); `breaking.txt` — pending interrupt line; `dj_speaking.lock` — idle-announce mutex
- `playlist.json` — ordered track names when a selection is active; `resume.json` — pause point
- `last_list.json` / `last_archive.json` — snapshots of the last `list` / `unarchive` listing so numeric selections stay stable
- `prompt_history.jsonl` — append-only generation log
- `.kokoro_python` — cached interpreter path (`dj.py`); `dj_engine.log` — which TTS engine spoke and why
- `prompts/enhance.md` — the enhancer's system prompt (read-only input, re-read on every `enhance`/`egen`). `enhance_file()` returns `ROOT/prompts/enhance.md` when it exists, else `CODE_DIR/prompts/enhance.md` (`ENHANCE_USER` / `ENHANCE_SHIPPED`), because a plugin's folder is replaced on update. An existing but empty data-dir copy still wins and produces "Enhancer instructions missing (<that path>)".
- `statusline.py` — copied here from the code folder by the SessionStart hook (see Statusline coupling)
- `llm/t5gemma-tokenizer.json` — SA3's tokenizer (read-only, optional) for the exact 256-token prompt check in `gen`/`enhance`/`egen`

**Archive + prompt history.** `radio.py archive` moves unwanted tracks to `<library>/_archive`. The exclusion from playback is structural, not a filter: `get_library()` (via `_audio_in()`) lists `.mp3`/`.wav` files **non-recursively**, so a subfolder is already invisible to shuffle and playlists — that's why `_archive` lives *inside* the library folder rather than beside it. `_archive_paths()` kills the player *before* moving when the target is on air (Windows refuses to move an open file; `_move_track()` also retries ~16× at 0.25s), then `_playlist_drop()` removes the moved names from `playlist.json`, deleting the file entirely when nothing is left. That drop matters: a playlist whose entries have all moved would otherwise leave `daemon_loop` spinning on `if not track.exists(): continue`. `cmd_unarchive` is the inverse and restores to the library only — never back into a playlist. Prompt history is append-only JSONL at `prompt_history.jsonl`, written by `history_add()` from inside `source_stability_api` on each successful save (so it records only tracks that actually landed); `cmd_egen` stashes the user's rough idea in the module global `GEN_IDEA` so the record carries both the idea and the enhanced prompt. **`cmd_enhance` logs too** (`kind="enhance"`, empty `file`), so a rewrite isn't lost because nothing was generated from it, and `prompts <n>` prints a `gen` line for it; `kind` is written only for enhance records, so older records stay generations. History numbering is the file position, so it is stable across new entries, and `_history_where()` marks each one `a`/`x` against the library and archive, `b` against `BAD_DIR`, or `e` for an enhance-only record. **`radio.py drop`** is `_archive_paths([now_playing], name, BAD_DIR, ...)`: the same kill-then-move-then-`_playlist_drop` path as a no-arg `archive`, but into `BAD_DIR` = `DEFAULT_OUTDIR / "bad song"`, one fixed shared reject pile, NOT relative to `OUTDIR` like `_archive`, so rejects from every collection meet there. It's a sibling collection under `output/`, invisible to other libraries for the same non-recursive reason, and playable with `folder "output/bad song"`, where `drop` refuses (source == destination). Tested on temp folders with a real `ffplay` holding the file open; the live daemon's advance after the kill is the same code path as `archive`/`skip` and was not re-run for `drop`.

**Source providers (pluggable).** Where music comes from is a strategy selected by `config.json` `source` and dispatched through the `SOURCES` dict in `radio.py`. Only `stability-api` exists today (async submit → poll `/results` → save as `<slug>-<stamp>-<i>.<output_format>` into `OUTDIR`, where `output_format` is `mp3` or `wav`, set by `radio format`). To add one, write a `source_*(prompt, count, duration)` function that returns `(tracks_saved, credits_spent_or_None)`, prints only its failures, and register it in `SOURCES`. A source that refuses before sending any request (no key) returns `NOTHING_SENT` in the credits slot, and `cmd_gen` prints `Cost: 0 credits (nothing sent)`; `None` is kept for a real submit whose balance change couldn't be read, so `Cost: unknown` never follows a refusal. `cmd_gen` owns the whole summary, refuses a count of 0 or a third number, and above `GEN_COUNT_CONFIRM` (20) tracks asks for a typed `yes` via `input()`, cancelling when there is no terminal.

**gen's output is a fixed four-line block**, to keep Claude's relay short: `Length: <who> <n>s`, `Prompt: <exact prompt sent>`, `Cost: <n> credits`, `Folder: <OUTDIR.name> / track(s) added: N / total: N tracks`, plus a `FAILED (<i>/<n>) ...` line per failed track. `<who>` is `user decided`, or whatever `pick_duration` returns. The skill tells Claude to relay the block verbatim, so don't add progress chatter back to it. **Cost is measured, not assumed:** `_balance()` reads `stability_api.balance_url` (`GET /v1/user/balance` → `{"credits": float}`) before the first submit, and `_spent()` re-reads after the last result. The ledger lags: a 5s track's 26-credit charge was measured still missing after `_spent`'s ~5s of re-reads, and was visible by the next manual check. So an unmoved balance after a charge returns None → `Cost: unknown`, never 0. Concurrent generations on the same key are counted in the delta.

**Output format (`radio format`).** `cmd_format` writes `stability_api.output_format` through `set_config`. `AUDIO_FORMATS = ("mp3", "wav")` is the single list for both what gen can save and what `_audio_in()` (library + archive scan) picks up, so adding a format means adding it there and checking the players. SA3's WAV is a real RIFF file (pcm_s16le, 44.1 kHz, stereo, 176,400 B/s, so 31.8 MB for 180s) and list/archive/unarchive handle it; daemon playback of WAV was verified on GitHub runners on 2026-10-13 with ffplay, mpv and cvlc (Linux) and afplay (macOS), while `mpg123` exited 1 on a WAV without playing it. **`wav+mp3`** (`BOTH_FORMATS`; `FORMAT_CHOICES` is what `cmd_format` accepts, `AUDIO_FORMATS` stays the scan list) sends `output_format=wav` once, saves to `OUTDIR / WAV_SUBDIR` (`_wav`), and `_wav_to_mp3()` encodes `OUTDIR/<stem>.mp3` with ffmpeg at `MP3_BITRATE` (128k, what the API's own MP3s measured by ffprobe). Billed once, one take, and `_wav` is invisible to the non-recursive scan just like `_archive`, so nothing plays twice. History records the MP3 name. `_ffmpeg()` mirrors `detect_player`'s `C:\ffmpeg\bin` fallback; `cmd_format` refuses `wav+mp3` without it, and if an encode still fails the WAV is moved into the library so the paid track plays. MP3-plays/WAV-in-`_wav` was chosen over the WAV playing or keeping both in the library. `archive`/`drop`/`unarchive` move only the MP3, leaving its master in `_wav`. `tests/test_gen_format.py` covers it with the API stubbed, including the ffmpeg-missing fallback; a real paid `wav+mp3` generation is untested.

**HTTP transport: `urllib` first, `curl` as fallback** (`_api_post` / `_api_get`). It was curl-only, for the OS trust store, until `api.stability.ai` started **refusing TLS 1.2** (alert 70): curl on Windows 10 is Schannel-backed with no TLS 1.3 (`SEC_E_ALGORITHM_MISMATCH`), so it cannot reach the API at all there, while Python's bundled OpenSSL negotiates TLS 1.3 fine. Two things the urllib path must keep doing, both load-bearing:

- **Send a `User-Agent`.** Cloudflare fronts the API and was seen to 403 the default `Python-urllib/x.y` with an HTML challenge page while `ai-radio/1.0` passed: the absence of the header was the failure, not its value. `USER_AGENT` is `terminal-fm/1.0` since the rename. On 2026-10-18 a keyless balance request with it got the API's own 401 JSON, but so did one with the default, so the challenge comes and goes and that check could not tell the two apart.
- **Honour `stability_api.ca_bundle`.** `_ssl_context()` falls back to the platform trust store, but a Windows root store was seen to fail the chain with `certificate has expired` even though ISRG Root X1 was present and valid to 2035; certifi's bundle verifies it. `""` = platform default, so machines without the problem are unaffected.

A transport failure returns `("", message)` — distinct from an HTTP error code — so DNS/TCP/TLS breakage surfaces its actual reason instead of curl's bare `HTTP 000` with stderr discarded.

The curl path itself is hardened: `_curl_run` feeds the `Authorization` header through a config on stdin (`-K -`) so the key never sits on argv where any local process can read it, and `_curl_post` uses `--form-string`, because `-F` reads a value starting with `@` or `<` as a file to upload and the prompt is user text. Both verified against a local `http.server`: the header arrived, and `@C:/missing.txt` was sent literally.

**The DJ speech pipeline** crosses three files and degrades at every step: `radio.py` (daemon or hook) → `dj.py say --file <queued line>` → `dj.py speak()` → `_kokoro_render()` → `kokoro_tts.py` → Kokoro-82M (`<data dir>/kokoro/kokoro-v1.0.fp16.onnx` + `voices-v1.0.bin`). `speak()` tries engines in order: **Kokoro-82M → Piper → macOS `say` → Windows SAPI (the "robotic" fallback) → espeak.** Every engine gets the text on stdin or from a file, never as an argv element (`say` reads stdin with no text argument, espeak with `--stdin`), so a line starting with `-` can't become an option. **`dj.py say` is the whole DJ** (three call sites in `radio.py`: queued line, breaking line, idle announcement), so every on-air line is Claude-authored or hook-generated and spoken verbatim with no LLM.

**Kokoro interpreter discovery (`_kokoro_python` in `dj.py`) is the crux of voice reliability.** The daemon/hook is often launched by an interpreter (e.g. `pythonw.exe`) that lacks `kokoro_onnx`, which silently drops the DJ to robotic SAPI. So `dj.py` does **not** trust `sys.executable`: it probes for *any* interpreter that can `import kokoro_onnx, soundfile` (config override → cached `.kokoro_python` → current → its `python.exe` sibling → `python`/`python3`/`py` on PATH → Pythons beside those, `PY_VOICE_MAX` down to 3.10: what `py -3.X` runs on Windows, `python3.X` on PATH elsewhere), caches the winner, renders to a **per-process** WAV (`_dj_<pid>.wav`, avoids cross-process clobber; stale ones older than 30 min are swept), and self-clears a bad cache on failure. Override with `dj.python` in `config.json`.

**Hook-driven narration.** The plugin's `hooks/hooks.json` runs `sh "${CLAUDE_PLUGIN_ROOT}/hooks/radio-hook.sh" SessionStart|Stop` (SessionStart matcher `startup|resume`, in the foreground, timeout 30s; Stop `async`, 60s); on the manual install, entries in `~/.claude/settings.json` call the same launcher or `radio.py hook ...` directly. `radio-hook.sh` probes `python3`, `python`, `py` with stdin from `/dev/null` (so the probe can't eat the hook JSON); on Windows the first candidate with a `pythonw.exe` beside it wins (a strict python3-first rule would pick a bare `python3.exe` on some installs; whether `python.exe` flashes a console was not observed), elsewhere the first that ran. The probe exits 1 on a Python older than the script's `min` (passed to the probe as its argument; the no-Python note names it too), and `RADIO_HOOK_PYTHONS` replaces the candidate list (the tests use it to simulate a machine with none). It then runs `radio.py hook <event>` with the hook's stdin inherited, output to `/dev/null`, exit 0 always. **With no usable Python**, SessionStart prints one JSON object, `systemMessage` for the user and `hookSpecificOutput.additionalContext` for Claude, with the install command per OS and an instruction not to search the disk; Stop prints nothing. That is why SessionStart is not `async`: interactive SessionStart hooks already run in the background (the user can type), but Claude's first response waits for them, so the note is in context before the first `/tfm`. Checked with a throwaway plugin under `claude -p` on 2026-10-17: the stream showed the hook's JSON and Claude quoted the additionalContext; whether the interactive UI displays the `systemMessage` couldn't be observed there. **Windows without Git for Windows:** Claude Code then runs hook commands in PowerShell (hooks docs), where `sh` doesn't exist, so neither hook runs. No command string was found that is valid in both sh and PowerShell and still probes interpreters, so README lists Git for Windows as a Windows prerequisite and `setup` reports it. `.gitattributes` pins `*.sh` to LF because a CRLF checkout breaks under `sh`. `cmd_hook` reads the hook's stdin JSON for `cwd`, `last_assistant_message` and `transcript_path`. **Stop input on CLI 2.1.296 carries `last_assistant_message`** (observed with a throwaway plugin hook that dumped its stdin; Stop keys: `background_tasks`, `cwd`, `effort`, `hook_event_name`, `last_assistant_message`, `permission_mode`, `prompt_id`, `session_crons`, `session_id`, `stop_hook_active`, `transcript_path`; SessionStart keys: `cwd`, `hook_event_name`, `session_id`, `source`, `transcript_path`). When the field is present (any string, even one `_clean_blurb` rejects) it is the only source and the transcript is never opened; only when it is absent does `_blurb_from_transcript` read the JSONL. `SessionStart` counts as "not finished": it never speaks idle, never reads the message or transcript, and only enqueues a generic line if music is playing. An async Stop hook of a `claude -p` run's final turn did not land before the process exited. On `Stop`:

- **music playing + `dj.breaking_news` off** → enqueue a line (capped at 4 pending, de-duped against the newest queued line);
- **music playing + `dj.breaking_news` on** → write the line to `breaking.txt` and kill the player; the daemon's `daemon_loop` inner while-loop sees the file on `wait()` return, speaks it (music paused via `speak_breaking()`), then **replays the same track from a seek offset** (`player_argv` injects `--start`/`-ss`/`--start-time` for mpv/ffplay/cvlc; afplay/mpg123 restart from 0). The file's presence is what distinguishes an *interrupt* from a *skip* (skip kills the player too but leaves no `breaking.txt`, so the loop advances). A second interrupt while one is pending is dropped. Off by default.
- **music stopped + `dj.announce_when_idle` on** → speak immediately, guarded by a stale-aware `dj_speaking.lock` so overlapping turns don't talk over each other. Off by default.

The narration text is Claude's own last assistant message, from `last_assistant_message` or else the transcript JSONL, run through `_clean_blurb` (strips markdown/code, drops questions/filler, keeps the most action-y 1-2 sentences); it falls back to a generic per-project line.

**The prompt enhancer (`enhance` / `egen`).** `enhance_prompt()` shells out to `llm/bin/llama-cli` (or `llama-cli` on PATH) with the first `.gguf` found by `sorted(LLM_DIR.glob("*.gguf"))` (CPU-only, `-ngl 0`, `--single-turn`, nothing stays resident) and returns `(prompt, None, conflicts)` or `(None, reply, [])`. The tested model is `qwen3-4b-instruct-q4km.gguf` = **Qwen3-4B-Instruct-2507**, Unsloth's Q4_K_M, a non-thinking build; with no binary or no gguf it prints "Enhancer not installed" and passes the idea through unchanged. **The system prompt is `prompts/enhance.md`, not code**, so it can be tuned as text; the data-dir copy wins (`enhance_file()`). `enhance_system()` re-reads it on every call and strips `<!-- -->` comments; missing or empty, the enhancer prints "Enhancer instructions missing" and passes the idea through. **Its body is revision 1.3** (2026-10-17): the v1.0 system instruction from `Qwen3_4B_SA3_Enhancer_Setup_v1.0.md` §2 (SHA-256 `ebe940c7…`, published there) rewritten to produce a one-line comma-separated caption in a fixed order (genre, 3-5 instruments with playing technique, production, mood, key, BPM last) with no scene or story words, artist names, negations, tags or song-section wording, following the owner's notes from a Gemini-based video-scoring pipeline. Key and BPM are for music only: an earlier home-grown prompt that forced an inline BPM made a chat notification come back "at 120 BPM" with "crisp percussion". **Tags are code's job** (`_tidy_caption`): told it could copy a supplied tag, the model invented ones ("Tag: TrackType: BossBattle") in 14 of 52 prompts; told to write none, it dropped a supplied one. So the instructions forbid tags, and `_tidy_caption` strips any `Label:` the model writes and "in no key", then puts the brief's own `TrackType:`/`Format:`/`Genre:` tags (the SA3 prompt guide's) back in front. An answer containing the hint's `clip length N seconds` is the brief echoed back (v1.2 once did exactly that), and `enhance_prompt` returns the missing-input reply for it; the check is built from the same string as the hint, so rewording one rewords both. **A/B, v1.0 against v1.3**: 29 briefs (the setup doc's 12 acceptance cases plus story, artist, scene, short-clip, sound-effect, non-English and negated-exclusion briefs), two samples each, through each version's real `enhance_prompt` with a scratch data directory. Briefs passing every check went from 31 to 43 of 52; prompts with a negation from 27 of 56 to 0 of 54; music prompts with a BPM from 4 to 25 of 38; length from 58-124 words to 19-64; time per rewrite from 20.4 s to 14.8 s. Artist names, scene words and unrequested vocals went to zero; a sound effect now sometimes gets a key (3 of 6). Missed by every version, as limits of the 4B model rather than code paths: "fast doom metal, clean guitars only" comes back slow and overdriven, "rainy night drive" gets rain sounds, a self-contradicting brief can get the vocal-model reply instead of a question (`egen` stops either way), and an injection-style brief returns the lofi example. No audio was generated from these prompts, so that captions make better music is the notes' claim, not a measurement. Sampling is the doc's §3 (`ENH_SAMPLING`: temp 0.7, top-p 0.8, top-k 20, min-p 0, `-n 512`). **Only a real rewrite may reach Stable Audio** (doc §4): `enhance_prompt` returns `(None, reply, [])` for the two fixed replies in `ENH_NOT_PROMPTS` (vocal/speech request, missing input; their wording must track `enhance.md`), for a reply ending in `?` (the instruction's clarification question), and for a rewrite over `SA3_PROMPT_TOKENS` (256) on both attempts (over-limit is retried once, like a contradiction; a runaway that hit the 512-token cap is far over it). `cmd_egen` then prints `Enhancer: <reply>` / `Nothing generated.` and stops; `cmd_enhance` prints the reply. An empty idea returns the missing-input reply without a model call. `_PROMPT_JUNK_RE` also strips `*` and backticks, because the model wrote `a soft *clink*` despite the no-Markdown rule. **Self-contradiction guard:** `_contradictions()` sentence-scopes a negation cue against `CONFLICT_TERMS` (percussion, vocals, reverb, bass) and returns pairs like `'no beats' vs 'soft, brushed drums'`; `enhance_prompt` retries once on a hit (a second temp-0.7 sample is usually clean) and returns the survivors as the third tuple value; `cmd_enhance` prints a `Conflict:` line, `cmd_egen` refuses to spend credits, logs the rewrite and points at `radio prompts <n>`. Negation is sentence-scoped on purpose: a wider scope false-flagged legitimately beatless prompts ("No percussion, rhythm, or beat structure"), and a false alarm costs a generation. Measured over 39 real prompts: 3 flagged, all genuine, no false positives. Not caught: fast-vs-slow contradictions. Captions are a single "sentence", so a negation there would scope over the rest of the line; v1.3 writes none, so the guard now mostly matters for a data-directory prompt that does. **Prompt limit: 256 T5Gemma tokens, enforced.** The SA3 technical report (arXiv 2605.17991) says text is encoded by a frozen T5Gemma (google/t5gemma-b-b-ul2) encoder into 256 embeddings and longer prompts are truncated; the SA3 repo's `docs/guides/model-overview.md` says every DiT variant including the API-only `large` uses that encoder, the tokenizer config adds no BOS/EOS, so all 256 are prompt. The hosted API still accepts `prompt` ≤ 10,000 characters, so an over-long prompt is billed and silently cut; treating 256 as the hosted limit is inference from the above. `prompt_tokens()` counts exactly with a stdlib port of the tokenizer: it reads `llm/t5gemma-tokenizer.json` (34.4 MB, loaded once in ~0.5s), matches added tokens (newline runs, `<table>`, `<eos>` ...) whole, then BPEs each gap as ONE word after space→U+2581 (Gemma's `Split(" ")` pre-tokenizer runs after the normalizer has already replaced every space, so it never splits), with byte fallback and a heap merging lowest rank, leftmost first. Verified on 2026-10-14 at 0 mismatches against HF `tokenizers` 0.22.1 over 8,117 distinct strings (prompts, every line of the repo's text files, random Unicode, emoji ZWJ, CJK, combining marks, special tokens, whitespace runs); 256 passes and 257 refuses; 10,000 characters count in 12 ms. Without the file it estimates `ceil(chars/4)` and says so; measured prose runs 4.16-5.33 chars/token but digits, chord symbols and Japanese 1.41, so the estimate undercounts dense text, and a word/char heuristic is no substitute (the best one tried overcounted prose up to 2.2x and undercounted digits, emoji and random letters). `cmd_gen` refuses before `pick_duration` and `_balance`, so a refusal spends nothing; `enhance_prompt` retries an over-limit rewrite once. v1.3 rewrites measured 29-93 tokens (v1.0: 74-167). **The enhancer doesn't pick a length; it is told one.**

**Length before the rewrite.** `cmd_enhance` and `cmd_egen` settle the duration first - `pick_duration(idea)` when the slot is empty or `auto`, otherwise the typed number - and pass it to `enhance_prompt(idea, duration=secs)`, which appends `(clip length N seconds - do not mention the length)` to the brief; the instructions use it to give a clip of 20 seconds or less fewer parts and no build words. Until v1.3 the hint also said "pace the description for it", the setup doc's "broad development appropriate to the supplied duration"; captions carry no arc, because the owner's notes found Stable Audio 3 ignores section instructions. `cmd_egen` writes the picked number into the args and hands `cmd_gen` a `decided=(who, note)` pair so the `Length:` line credits the picker and the typed-number-under-10 refusal doesn't fire on a picked 5s; `cmd_gen` still auto-picks for plain `gen`. The hint is one line because a two-line brief leaked llama-cli's echo of the second line into the prompt (`_strip_cli_chrome` skips only the echo's first line, and `_split_duration` then ate "duration: 120 seconds"), and it says not to mention the length because the model otherwise narrated it ("spanning 90 seconds"). Verified with a real `egen "lofi coffee music"` under v1.0: 150s picked from the idea, file 150.000s by ffprobe. Length stays `pick_duration`'s job because asking the 4B model for a `DURATION:` line in the rewrite gave erratic lengths at temp 0.9 (dark techno 30s, synthwave 30s) while `pick_duration` at temp 0 was consistent; `_split_duration` still strips a stray `DURATION:` if the model adds one anyway.

**Auto duration (`pick_duration`).** When `gen` gets no duration, or the literal word `auto` in the duration slot (the only way to auto-pick with a count: `gen "..." 3 auto`), `cmd_gen` calls `pick_duration(prompt)` → `(seconds, who, note)` for the `Length:` line; `enhance`/`egen` call it on the **idea**, before the rewrite (above). **A length written in the text short-circuits the model** (`_stated_duration`, `who="as stated"`): the model ignored a stated 90 and returned its trailer anchor of 120s at temp 0. The regex demands a spelled-out unit so `80s synthwave` stays a decade, and a lookahead drops sound-timing numbers (`8 second reverb tail`); `tests/test_durations.py` pins 17 strings, including `74 BPM` and `6/8` ignored and `600 second` clamped to 380. Otherwise it runs the same llama-cli model through `_llm_run()` at **temp 0**, so a given prompt always gets the same length, with a system prompt built from `DUR_RULES` (`_dur_guide`/`_dur_sys`); one pick is a CPU call measured at 8.9-13.5s. The answer is parsed with `_DUR_RE` (bare-number backstop, 1-4 digits) and clamped to `[ENH_DUR_MIN, ENH_DUR_MAX]` = **1-380s**. A clamp shows as ` (model said Ns)`. With no model installed, or an answer with no number, the first `DUR_RULES` keyword (word-boundary match, checked in order: notification/sting 5s → jingle/bumper 15s → intro/outro/commercial 30s → ambient/drone/sleep 300s → techno/trance/progressive 240s → trailer/punk 120s → common genres 150s) decides (`keyword rules decided`), and no match falls back to `stability_api.duration` (`config default`). There is deliberately **no on/off setting**: an omitted duration always auto-picks and a typed one never does, so the typed number is the opt-out. The rule lengths are taste defaults, not measured optima. Neither end of 1-380 is a verified SA3 limit: 5s and 218s are the shortest and longest confirmed.

**`llama-cli` writes its chrome to STDOUT, so it must be filtered.** The ASCII banner, `build:`/`model:`/`ftype:` lines, the slash-command help, the echoed input after a `> ` marker, the `[ Prompt: ... t/s ]` timings and `Exiting...` all arrive on **stdout**, not stderr, and `--log-disable` does **not** suppress them (verified on build b10069; a real `enhance` through b11581 came out clean on 2026-10-13). `_strip_cli_chrome()` keeps only the text between the `> ` echo and the timing footer, with a chrome-line regex as backstop if a future build drops the marker; `_PROMPT_JUNK_RE` then removes angle brackets/quotes the model sometimes copies from placeholder syntax. Without that filter the entire banner — build string, gguf path and command list — was sent to Stability as the music prompt. Don't try to fix this with `-no-cnv`: without `--single-turn` it never exits and floods stdout with `> ` prompts.

**config.json** is a shallow-merge overlay: `load_config()` deep-copies `DEFAULT_CONFIG` and per-key merges the user file (dict values update, scalars replace). `dj.py` has its own `DJ_DEFAULTS` merged the same way from the `dj` section, and `set_config(section, key, value)` is the only writer — the `announce`/`breaking` toggles persist through it.

## Gotchas

- **The repo's `.gitignore` excludes every data-directory file, the key and the models**, because on the manual install the clone at `~/.claude/terminal-fm` is also the data directory. `release_check.py` (run before any push) fails on a home-directory path, a personal email address, a key pattern, a file over 5 MB, or a force-added runtime file. Identifying strings (a username, an email) go in the untracked `.release_markers`, never in the script, because a list inside a shipped file publishes what it guards. Each line is also matched with adjacent string literals joined (`JOIN_RE`), so `"ab" + "cd"` can't slip past, and a marker hit is reported by line number only.
- **`examples/` ships with every install.** A plugin install copies the whole repo, so the demo video, track and voice sample (about 5 MB, each file under `release_check.py`'s 5 MB limit) land in every user's plugin folder. `release_check.py` only size-checks binary files, so check a new media file's metadata and bytes for identifying strings by hand before adding it.
- **`radio folder` creates before it saves, and the import-time `OUTDIR.mkdir` is guarded.** A `library_dir` that can't be created used to be written to `config.json` first and then crash every later command at import; now `cmd_folder` refuses with `Not saved`, and import falls back to `DEFAULT_OUTDIR` with a warning on stderr.
- **`parse_selection` clamps to `1..n` before building the range.** Iterating the typed range and filtering afterwards made `1-50000000` take 1.26 s, and one more digit hung the command.
- **`cmd_pause` requires a live player, checked after the daemon is dead.** Between tracks `state.json` still names the track that just ended, and saving a resume offset then would point past its end; it stops cleanly instead and says nothing is resumable. The same happens when no offset over 1 s was saved (a track that started during the daemon kill), so status `paused` always has a `resume.json` behind it.
- **`cmd_play` refuses before it queues `--say`.** An empty library or a missing player returns before `queue_add`, so a refused sign-on isn't spoken on some later `play`. When a daemon is already playing, the line is still queued (the running radio speaks it before its next track).
- **Never add the marketplace from a data directory.** A local-path `claude plugin marketplace add` plus `install` copied the whole folder (on the manual install the code dir is the data dir) into `~/.claude/plugins/cache/digitalbyte/ai-radio/1.0.0/` (the plugin's name then) as plain files with no `.git`: several GB including `.key`, `config.json`, `output/`, `llm/`, `kokoro/` and every untracked file, and `uninstall` left it behind marked `.orphaned_at`. The `.gitignore` only protects the GitHub route, which clones. Test installs come from GitHub or a clean clone or zip of a release commit.
- **An installed plugin overwrites this checkout's `statusline.py` at every session start** when the checkout is also the data directory (`~/.claude/terminal-fm`): `_install_statusline` copies the installed version over it, because the two aren't the same file. A local edit to `statusline.py` was silently reverted this way on 2026-10-18. Commit it before starting a new session, and check `git status` for it afterwards.
- **`play --say` jumps the DJ queue; every other line is FIFO.** `queue_add()` writes `<time_ns>-<rand>.txt` and `speak_next()` reads the lowest-sorting name, one line per track. `queue_add(text, front=True)` (only `cmd_play`'s `--say` passes it) prefixes `0-`, which sorts ahead of every timestamped name, so a sign-on is spoken before the first track even with hook lines pending. Several sign-ons stay FIFO among themselves. The hook's de-dupe compares against `pending[-1]`, which stays the newest normal line unless every pending line is a sign-on.
- **`gen` number grammar is position-sensitive and deliberately NOT `[count] [duration]` for the one-number case.** ONE number after the prompt is the duration (`gen "..." 147` = a single 147s track); TWO are count then duration. The count-first reading once nearly turned `gen "..." 218` into 218 tracks (~4,360 credits). A lone number under 10 is refused rather than generating a 5-second track (the refusal suggests `gen "<prompt>" N auto`). No number at all means auto-pick, and `auto` is accepted in the duration slot (`gen "..." 3 auto`); any other non-numeric token prints usage. The under-10 refusal applies only to a typed number; the auto-pick can and does choose under 10s. There is no `steps` argument: SA3 is fixed at `steps=8` from `config.json`. `cmd_egen` passes the caller's numbers straight through, so the same rules apply.
- **`ENH_DUR_MIN`/`ENH_DUR_MAX` (1-380) bound only the auto-pick**, not an explicit duration passed to `gen`. 1-380s is the API's documented `duration` range (default 190), and the price when checked in September 2026 was a flat 26 credits per successful generation, failed ones free. Tested: SA3 returned exactly 218.0s for a 218s request (ffprobe) and 5.0s for a 5s one, and that 5s track's balance drop was 26 credits. The names still say "ENH" from when the enhancer recommended lengths, and `readme_check.py` reads them by name.
- Each generated track costs Stability credits (measured, printed on the `Cost:` line) and is saved permanently into the **active library folder** (`OUTDIR`), which is `output/` only when `library_dir` is unset. New files are auto-picked-up on the daemon's next shuffle pass — no restart needed.
- **`library_dir` may already point at a subfolder.** Run `radio.py folder` before assuming `output/` is what plays or where `gen` lands. `OUTDIR` is read once at import (`resolve_outdir()`; `~`/env vars expand, relative paths resolve against `ROOT`), so a running daemon needs `stop`/`play` to pick up a change. The glob is non-recursive, so pointing at a subfolder plays just that collection.
- **`main()` forces stdout/stderr to UTF-8** (`reconfigure(encoding="utf-8", errors="replace")`). Piped output on Windows otherwise uses cp1252: "café" reached Claude as "caf�" and any non-cp1252 character (☕, →, CJK) raised `UnicodeEncodeError` on gen's `Prompt:` line before submitting; the bytes actually sent were always UTF-8. `pythonw` (the hooks) has no stdout; the `try` covers that.
- The statusline re-runs on each turn and every `statusLine.refreshInterval` seconds, so the *display* can lag that long. `nowplaying.txt` itself is current: it, `state.json` and the live player's command line were observed naming the same track while the statusline still showed the previous one.
- Almost all error handling is intentionally swallowed (`except Exception: pass`) so a broken DJ / missing engine / missing model never takes down playback. When debugging, `dj_engine.log` is the observability seam — prefer reading it over adding prints that would be discarded by the detached daemon's `DEVNULL` stdio.
- The library folder is the source of truth for tracks; there is no database or index.
